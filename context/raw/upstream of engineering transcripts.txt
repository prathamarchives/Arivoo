The agent-native software repository
The core idea is this: a repo should not merely contain the software. It should contain the knowledge, constraints, and verification machinery that make producing the next correct version of that software easier than producing an incorrect one.
A conventional repository stores code that engineers understand. An agent-native repository goes further. It encodes enough of the system's intent and structure that an agent can understand where a change belongs, determine what it is allowed to change, implement the change, test it, diagnose its own failures, and produce evidence that the result works.
This is an engineering discipline, not a prompting technique.
OpenAI described a version of this approach in February 2026: repository knowledge as the system of record, mechanically enforced architectural boundaries, direct agent access to application behavior and observability, and a feedback loop that converts engineering failures into better tooling.

The next step is to treat these ideas as a complete system rather than a collection of best practices.
1. The fundamental model: a repo is an executable memory system
Think of the repository as five interconnected systems.

1. Intent memory
Why the system exists, what its concepts mean, what behavior is required, and which trade-offs have been decided.




2. Structural memory
Types, module boundaries, APIs, schemas, ownership, dependency directions, and approved primitives.




3. Verification memory
Tests, contracts, static analysis, architectural checks, reproducible scenarios, and explicit acceptance criteria.




4. Operational memory
Logs, traces, metrics, error reports, runtime state, and tools that let an agent reproduce real failures.




5. Evolutionary memory
Past mistakes, rejected approaches, architectural decisions, regressions, and improvements to the engineering environment.



These systems must agree with one another. A design document that contradicts the types is not good memory. A test suite that fails to detect a known bug is not good verification. A log that says an operation failed without exposing the relevant state is not good operational memory.
The goal is not to maximize documentation or add the most tools. It is to minimize the distance between what the system should do, what the code actually does, and what the agent can establish about that difference.
I would formulate the central rule as follows:
Every important engineering decision should exist in a form that the agent can discover, and every important enforceable decision should exist in a form that the machine can check.

That distinction is critical. Natural-language guidance is useful for interpretation. Executable constraints are what prevent an agent from repeatedly violating the same rule.
2. How a repository should start
Start by making one complete change reliable. Do not start by building a giant engineering framework.
The first objective is to establish one path from intent to working software:
Requirement → implementation → verification → evidence → merge
Only after that path works should you add infrastructure to make it faster, stricter, and more autonomous.
The initial structure
For a small or medium-sized project, I would begin with this:
repo/
├── AGENTS.md
├── README.md
├── ARCHITECTURE.md
│
├── docs/
│   ├── product/
│   │   └── invariants.md
│   ├── decisions/
│   └── plans/
│
├── src/
│   ├── domain/
│   ├── application/
│   ├── adapters/
│   └── entrypoints/
│
├── tests/
│   ├── unit/
│   ├── integration/
│   ├── contracts/
│   └── acceptance/
│
├── scripts/
│   ├── bootstrap
│   ├── dev
│   └── verify
│
└── .github/
    └── workflows/
        └── verify.yml


This is a starting shape, not a mandatory hierarchy. A small library might need no application/ or adapters/ directory. A frontend application might have a different structure. Introduce a layer when it establishes a real boundary.
Each file has a distinct job.
Artifact	Purpose
README.md	Explain the project and get a new machine running.
AGENTS.md	Give agents the shortest reliable map of the repository and its working conventions.
ARCHITECTURE.md	Explain component boundaries, dependency direction, and the main data flows.
invariants.md	Record the behaviors and guarantees that must remain true.
decisions/	Preserve important decisions, their reasons, and rejected alternatives.
tests/	Make expected behavior executable.
scripts/verify	Provide a standard way to establish whether a change is acceptable.
CI configuration	Apply the required checks independently of the agent's claims.
Do not create every file just to fill out the tree. Add a document when a real decision needs to be preserved. Add a test category when you have tests that need that distinction.
One important detail: AGENTS.md must not become the entire brain of the project. It should explain where to find authoritative knowledge, which commands to run, and which constraints apply everywhere. Detailed knowledge belongs near the relevant domain or in a dedicated document.
OpenAI's engineering team arrived at a similar structure after finding that a single, large instruction file became difficult to maintain, verify, and navigate. They instead used a short entry point and a structured, versioned knowledge base. Source
The first three engineering assets
I would build these in order.
First: a product contract.
Write down what the system must do, not how every function must work.
For example, an application's product contract might say:
- A saved object must survive an application restart.
- A failed write must not be reported as a successful save.
- A user must not access another user's private data.
- An import must not silently overwrite an existing object.
- A relationship between two objects must refer to objects that exist.
These are illustrative guarantees, not requirements for every project.
The key is to separate three categories:
- Behavior: what users must observe.
- Invariant: what must always be true.
- Implementation choice: how the code achieves it.
Agents should have substantial freedom over implementation choices. They should have very little freedom to violate important invariants.
Second: a golden path.
Build one small feature that demonstrates the approved way to implement a complete feature. It should cross the relevant system boundaries and include validation, error handling, tests, and observable behavior.
If the project has a backend, the golden path might be one operation that accepts a request, validates it, applies a domain rule, persists data, and returns a typed response.
That feature becomes the canonical example. Future features extend it instead of inventing an entirely new approach.
The golden path matters more than ten pages of coding rules because agents are strongly influenced by the patterns already present in the codebase. An example teaches the implementation shape; constraints determine whether deviations are allowed.
Third: one verification command.
Create a single entry point, such as:
./scripts/verify


It should run the appropriate checks for the project. Typically, that means formatting, linting, static type checking, tests, and a production build. Add architecture checks, migration validation, or security checks when the project needs them.
Run the same underlying checks locally and in CI. Avoid a situation where the developer's local workflow and the CI workflow enforce different rules.
The command must return a nonzero exit status when a required check fails. Its output must identify the failing check and provide enough detail to diagnose the problem.
Do not build a sophisticated agent orchestration system first. Give the agent a reliable way to understand the code, run the application, and verify a change. Then improve that environment in response to actual failures.
3. The first new principle: every failure must become an asset
I would make this the central operating rule of an agent-native repository.
A failure should either fix the current implementation or permanently improve the system's ability to prevent, detect, or diagnose that class of failure.
This does not mean every typo needs a new lint rule. It means recurring or costly failures must not remain only in someone's memory or disappear when a chat session ends.
Use this loop:
Observe a failure
Bug, review comment, test failure, duplication, architectural drift

Preserve a reproducible example
Regression test, fixture, trace, failing command, or concrete counterexample

Identify the missing capability
Missing context, weak abstraction, missing type, missing check, weak test oracle, or poor tooling

Fix at the strongest appropriate layer
Improve the primitive, schema, type, architecture rule, test, diagnostic, or documentation

Verify the guard itself
Prove that the original failure is now caught or made harder to produce


Consider a concrete example.
An agent adds a third implementation of request validation. The new implementation handles malformed input differently from the existing implementations.
A weak response is to ask the agent to follow the existing pattern next time.
A better response is to determine why three valid implementations were possible in the first place. Perhaps validation is duplicated across endpoints. Perhaps there is no shared schema. Perhaps the correct primitive is not discoverable.
The resulting fix might be a shared validator, a schema-driven API, and a static rule that prevents the old pattern from returning.
The strongest fix is not necessarily the strictest rule. It is the smallest architectural change that removes the underlying source of repeated error.
OpenAI describes the same progression in its own terms: when agents struggle, engineers identify the missing tools, abstractions, or guardrails; observed mistakes eventually become mechanically enforced principles and recurring cleanup tasks. Source
Classify the failure before fixing the harness
Not every failure needs a new rule. First identify its cause.
Failure class	Likely durable remedy
Agent misunderstands a product requirement	Clarify the product contract and add an acceptance test.
Agent guesses an external data shape	Validate the boundary or use a typed SDK.
Agent reimplements an existing utility	Improve the canonical API; add a check if duplication remains possible.
Agent changes unrelated modules	Reduce coupling and clarify ownership or dependency boundaries.
Agent produces complicated code	Improve abstractions and add targeted complexity checks.
Tests pass despite incorrect behavior	Strengthen the test oracle, not merely test count.
Agent cannot reproduce a bug	Add fixtures, replay tools, better logs, or an isolated runtime environment.
Documentation disagrees with code	Establish a source of truth and generate or validate derived documentation.
A single low-severity error may need only a code fix. A repeated failure needs a structural response. A single severe security or data-integrity failure may justify a permanent guard immediately.
That is how the repo learns without accumulating hundreds of arbitrary rules.
4. The constraint ladder: move from advice to construction
Here is the engineering hierarchy I would use when an agent keeps making the same mistake.
0

Prose
"Always validate incoming data." Useful, but dependent on the agent remembering and interpreting the instruction.


1

Canonical examples
A working endpoint demonstrates the approved approach.


2

Approved primitives
A shared parser or typed API makes the correct approach easy to reuse.


3

Types and contracts
Invalid states become unrepresentable within the relevant typed boundary, or invalid inputs are rejected at runtime.


4

Static and structural checks
Linters and dependency checks reject forbidden patterns before execution.


5

Executable verification
Unit, integration, contract, and acceptance tests establish observable behavior.



Enforced invariants
CI gates or restrictive APIs prevent a change from being accepted without satisfying the required conditions.



This is a conceptual ladder, not a rigid sequence. A type checker and a test suite solve different problems. Runtime checks remain necessary at untrusted boundaries. Some requirements cannot be verified mechanically and still need human judgment.
But the direction is clear: when an instruction matters enough to repeat, investigate whether it should become an enforced property of the system.
For example, suppose the rule is:
Do not access the database from UI components.

A prose rule is a weak first defense. A canonical repository interface is better. A dependency graph that forbids UI-to-database imports is stronger. A module architecture in which UI code cannot access database credentials or capabilities directly is stronger still.
The objective is not to make every decision impossible. It is to make the dangerous decisions unavailable and leave legitimate design choices open.
Principle 2: reduce the agent's search space
Every independent implementation path is another opportunity for inconsistency.
Suppose an application has six ways to access the same database, four ways to validate requests, and three patterns for reporting errors. An agent must infer which combination is appropriate for every new feature.
A well-designed repository reduces those choices.
Provide one approved database interface, one error model, one boundary-validation approach, and one normal way to introduce a new application capability. Add an alternative only when it solves a real problem that the canonical approach cannot solve.
This is not a demand for one giant framework. It is a demand for a small set of reliable primitives.
A useful design test is:
Can an agent build a new feature by composing existing capabilities, or must it invent new architecture every time?
The former scales. The latter produces architectural drift.
There is a limit, though. An abstraction that hides behavior, complicates debugging, or forces unrelated concepts together can make the search space smaller while making the system worse. Prefer primitives that reduce duplication without concealing important semantics.
Principle 3: make violations harder than compliance
A useful rule has three properties:
1. The approved path is obvious.
2. The approved path requires less work than an alternative.
3. The system detects important deviations.
Consider migrations. Asking an agent to remember not to edit a production database manually is weaker than providing versioned migrations, a standard migration command, a test database, and a CI check that verifies migrations can run from a clean state.
The structure makes the correct workflow the natural workflow.
This applies equally to authentication, file access, error handling, API contracts, application state, and UI primitives.
Principle 4: improve the abstraction when rule count grows
A repository with 300 individual rules may be encoding a poor architecture.
If many rules prohibit slightly different forms of the same mistake, look for a deeper invariant that unifies them.
For example:
- Several rules prohibit different forms of direct external API access.
- A typed adapter boundary eliminates most of those cases.
- One dependency check verifies that the boundary remains intact.
- The adapter owns error mapping and data validation.
Instead of memorizing every bad pattern, the agent learns and uses one safe interface.
A growing list of rules is sometimes evidence that the abstraction is missing.
The aim is to reduce both the number of mistakes and the number of rules needed to prevent them.
5. New principle: changes should carry their own proof
An agent must not declare a feature complete merely because it has written code or because a test command exited successfully.
Every meaningful change should have an evidence package appropriate to its risk.
Call this proof-carrying changes.
For a simple bug fix, that might mean a regression test showing the original failure and a successful run of the required checks.
For a UI change, it might include a reproducible browser scenario, screenshots, and evidence that the relevant interaction works.
For a database migration, it might include successful application to a clean database, preservation of existing data, and correct behavior after the migration.
For a performance change, it might include measurements before and after under the same workload.
The evidence should answer four questions:
- What was the intended behavior?
- How was the original problem reproduced?
- What changed?
- What independent observation demonstrates that the fix works?
OpenAI describes an agent workflow that reproduces bugs, records videos of failures, implements fixes, validates the result by driving the application, and produces a second demonstration. The important idea is that the agent can observe the real system rather than rely only on source-code inspection. Source
Verification must not share all the same failure modes as implementation
There is a subtle problem with agent-generated tests: the same misunderstanding can affect both the implementation and its tests.
The agent may implement the wrong behavior and then write a test that confirms that behavior.
This means two properties must remain separate:
Test execution: Does the implementation satisfy the assertions?
Test validity: Do the assertions express the correct requirements?
The first is mechanically verifiable. The second requires better oracles: product contracts, independently established expected results, reference implementations, known examples, domain invariants, or external observations.
Useful techniques include:
- Regression tests: preserve behavior that previously failed.
- Property-based tests: check general properties across many generated inputs.
- Mutation testing: deliberately change implementation behavior and check whether the tests detect it.
- Contract tests: ensure boundaries respect agreed data and behavior contracts.
- Acceptance tests: verify important user-visible outcomes through the real system.
Coverage alone is insufficient. A test may execute every relevant line without detecting incorrect behavior. Martin Fowler's 2026 investigation of maintainability sensors documents this distinction and demonstrates the value of mutation testing in exposing weak assertions. Source
For critical paths, I would prefer a small, strong test suite with meaningful failure detection over a large suite that merely produces an impressive coverage percentage.
Protect the verifier itself
There is another risk: an agent can make a test pass by weakening the test, removing the assertion, skipping the check, or altering the acceptance criteria.
A repository needs a distinction between changing application behavior and changing the machinery used to judge that behavior.
Treat the following as higher-risk changes:
- Removing or weakening tests.
- Changing CI gates.
- Adding lint suppressions.
- Altering security rules.
- Modifying migration validation.
- Changing expected acceptance results.
Require a reason and appropriate review for these changes. For a mature system, protect critical verification files with ownership rules and make policy changes explicit.
Otherwise, the system can gradually learn to look correct without becoming more correct.
6. New principle: diagnostics are part of the architecture
Most software tools treat errors as messages for human developers. In an agent-native repo, an error is also an instruction to the next reasoning step.
Compare these outputs.
Weak:
Architecture check failed.


Better:
ARCH-012: UI module imports a database adapter.

Violation:
  src/ui/library-view.tsx
    -> src/adapters/database/library-repository.ts

Why:
  UI modules must depend on application interfaces,
  not infrastructure implementations.

Fix:
  Move the operation behind the existing library
  application interface and import that interface.

Relevant contract:
  docs/architecture/module-boundaries.md


The second error makes the problem, reason, approved path, and relevant knowledge available immediately.
This is a major multiplier. The agent does not need to search for the intended architecture, guess the rationale, or spend several iterations discovering the correct repair.
I would require every custom lint or structural check to provide:
- A stable rule identifier.
- The exact violation and location.
- The invariant being protected.
- An actionable repair path.
- A reference to the relevant design contract.
OpenAI reports that its custom lint diagnostics include remediation guidance specifically to improve agent self-correction. Martin Fowler also found that targeted diagnostic text could influence how agents repaired complexity violations and managed exceptions. OpenAI · Fowler
There is a further opportunity: create small diagnostic commands that tell an agent what to inspect next. Instead of requiring it to decode an enormous log file, provide commands such as:
./scripts/verify --changed
./scripts/verify --explain ARCH-012
./scripts/test --related-to src/domain/library
./scripts/diagnose --run-id <id>


These are illustrative interfaces. Implement them when they solve actual workflow problems.
The principle is simple: make the next correct action easier to identify than the next speculative action.
7. Your codebase is memory, but not all memory should look the same
The statement that a codebase is memory is correct, but it needs a more precise model.
A repository contains different kinds of knowledge. They should not be mixed into one instruction file or duplicated across several competing documents.
Memory type	Where it belongs	What it answers
Intent	Product specifications and invariants	What should happen?
Structural	Types, schemas, interfaces, dependency rules	What can depend on what?
Behavioral	Tests and executable contracts	What behavior must continue to work?
Explanatory	Architecture documents and decision records	Why is the system designed this way?
Operational	Logs, traces, fixtures, runbooks	What happened, and how can it be reproduced?
Temporary	Active execution plans and task notes	What remains to be done on this change?
The important part is that each fact should have an authoritative home.
Suppose the maximum supported upload size is 20 MB. Do not independently hardcode that value in the frontend, backend, API documentation, and agent instructions.
Define the relevant contract once. Derive other representations where practical. Validate the behavior at the boundaries that matter.
This leads to another principle:
Every duplicated fact creates a synchronization obligation.
Some duplication is useful. A decision might be summarized in an architecture overview and explained in detail in a decision record. But the summary should point to the authoritative record, not become a second independent specification.
The same applies to plans. Plans are not permanent truth. An execution plan can become stale as the implementation changes. The source code, accepted specification, tests, and recorded decisions must not silently disagree with it.
Treat decisions as reusable knowledge
A good decision record should explain the problem, the selected approach, the alternatives considered, the reason for the choice, and any conditions that could justify revisiting it.
For example:
Decision: All external input is parsed at a boundary.

Reason:
Internal domain logic should not depend on guessed
or unvalidated external data shapes.

Enforcement:
- Boundary schemas
- Strict internal types
- Architecture checks

Rejected approach:
Repeated ad hoc checks throughout business logic.

Revisit when:
A new integration requires a materially different
trust or compatibility boundary.


This is much more valuable than an instruction saying "write clean, robust code." It gives future agents the rationale behind the architecture and shows how to comply.
8. Architecture should remove entire classes of agent mistakes
The previous principles become more powerful when applied to system architecture.
Consider four increasingly strong designs for an application that must prevent unauthorized data access.
Design A: Prompt-only. The agent receives a rule to check authorization.
Design B: Shared implementation. All protected operations use a common authorization service.
Design C: Restricted architecture. Modules cannot reach protected resources without passing through the approved boundary.
Design D: Restricted capability. Components that do not need protected resource access never receive the credentials or capability required to access those resources directly.
Design D removes an entire class of accidental access paths. It does not eliminate every authorization bug, but it reduces how much the agent must remember.
This illustrates a further principle:
Do not ask an agent to remember a property that the architecture can enforce.
Apply it to the problems that matter most.
Types should communicate domain meaning
Avoid representing every identifier as an undifferentiated string.
If a system has users, documents, and workspaces, distinct identifier types can prevent accidental substitution. Typed states can distinguish an unvalidated request from a validated domain object. Explicit result types can distinguish success from recoverable failure.
In a typed language, these ideas might look like:
type UserId = string & { readonly __brand: "UserId" };
type DocumentId = string & { readonly __brand: "DocumentId" };

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };


This is illustrative TypeScript. A production implementation would also need safe constructors or parsers that validate external values before assigning these types. A branded string alone does not validate anything at runtime.
The goal is to encode semantic distinctions once, so they propagate through the system instead of being re-explained at every call site.
Give each module a defined ownership boundary
When two modules can directly alter the same data, they can develop incompatible assumptions about its lifecycle.
Prefer a clear owner for each domain concept. Provide an explicit interface for other modules to use. Enforce dependency directions with static analysis or architectural tests when the codebase is large enough to justify them.
Do not introduce a rigid, multi-layer architecture into every small project. But once a system has several domains, integrations, or user interfaces, explicit boundaries become a major aid to both agents and human maintainers.
The criterion is not whether the architecture looks sophisticated. It is whether a change in one part of the system stays within a predictable scope.
Measure locality, not just code quality
If adding one field to a domain object requires changing 35 unrelated files, the agent may not be the real problem. The architecture may have spread that concept across too many boundaries.
Track how many modules a typical change touches, how often the same transformation is implemented in multiple places, and how frequently one domain's change breaks another.
A growing change footprint is evidence of coupling. It should trigger architectural investigation.
In her 2026 work on maintainability sensors, Birgitta Böckeler describes agents introducing duplicated request handling and inconsistent parameter passing, along with dependency checks and semantic architecture reviews that help detect these problems. Source
The lesson is broader than code duplication: repeated mistakes often reveal a missing boundary or an abstraction that does not express the true domain.
9. The repository must continuously clean itself
Even a well-designed repository will accumulate bad patterns.
A constraint that worked last month may no longer be sufficient. An agent may discover a workaround. A dependency update may change behavior. A once-reasonable utility may become redundant.
This is architectural entropy.
The solution is a recurring maintenance process. I would call it repository garbage collection.
An automated maintenance agent periodically examines the codebase for specific forms of drift:
- Duplicated business logic and utilities.
- Growing function or module complexity.
- Forbidden dependencies between modules.
- Stale documentation and broken internal links.
- Unused feature flags, obsolete code paths, and outdated workarounds.
- Weak or missing tests around important behavior.
- Lint suppressions and weakened checks.
- Inconsistent error handling or external API access.
Some findings should use deterministic tools. Others, such as questionable module responsibilities, require semantic review by an agent.
The cleanup agent should generate narrow, verifiable changes. It should not rewrite half the codebase because it thinks the code would look cleaner.
A sensible policy is:
1. Find a specific deviation.
2. Explain the invariant it violates.
3. Propose the smallest correction.
4. Run the relevant checks.
5. Submit a focused change.
Track the debt until it is corrected or explicitly accepted.
OpenAI describes using recurring agent tasks to scan for architectural and quality drift, update quality assessments, and submit targeted refactoring changes. Its engineers moved from manual, periodic cleanup to continuously enforced principles. Source
One refinement I would add is a ratchet policy. For selected quality measures, prevent new code from making the baseline worse. If legacy code already exceeds an acceptable complexity threshold, establish a baseline and require new code to meet the stronger standard. Improve the legacy baseline incrementally.
This prevents a cleanup effort from becoming all-or-nothing.
10. New principle: constraints themselves must be engineered
It is easy to create a rule. It is harder to create a rule that works without producing noise or encouraging workarounds.
A constraint should be treated as a small software product.
It needs an intended outcome, a means of enforcement, a way to test that enforcement, and a policy for legitimate exceptions.
I would use this standard for every important custom check:
Property	Question
Purpose	Which concrete failure does this prevent or detect?
Scope	Which code and situations does it apply to?
Precision	Does it reject valid implementations unnecessarily?
Diagnostic quality	Does it tell the agent why the violation matters and how to repair it?
Testability	Can we demonstrate both a forbidden case and an allowed case?
Exceptions	Can a legitimate exception be made without silently disabling the rule?
Drift	Will the rule remain accurate as the architecture changes?
For example, a complexity rule might accidentally encourage an agent to split one large function into 20 tiny functions that obscure the control flow. If the rule only measures function length, it can make the code worse while technically passing.
A better check evaluates a combination of factors and provides guidance for self-correction. Some properties are appropriate for static enforcement; others need an agent's semantic judgment.
Martin Fowler's work on coding-agent maintainability sensors describes exactly this kind of trade-off: individual complexity rules can conflict, and a rule that produces pressure in one dimension can cause undesirable patterns elsewhere. Source
My rule would be:
Every enforcement mechanism needs its own failure tests and an explicit way to handle exceptions.
Do not trust a linter just because it is called a linter. Verify that it detects the bad pattern, accepts legitimate code, and produces useful diagnostics.
Exceptions should be visible and justified. For long-lived exceptions, record an owner or a condition for reconsidering them. If a check repeatedly produces false positives, repair the check instead of teaching every future agent to ignore it.
11. New principle: the engineering environment needs regression tests too
This is one of the more useful extensions of the original thesis.
Most repositories test the product. Agent-native repositories should also test whether the engineering environment remains effective at producing correct changes.
Consider a future edit to AGENTS.md, a shared primitive, or the architecture checks. The product's existing tests might all pass, yet the change could make agents less effective.
You need some way to detect that degradation.
Maintain a small collection of representative engineering tasks, for example:
- Add a field to an existing domain object.
- Add an endpoint that accepts malformed input safely.
- Fix a reproduced bug without changing unrelated behavior.
- Extend an existing feature through the approved module boundary.
- Add a UI interaction and validate it in the running application.
- Perform a schema migration without losing existing data.
For each task, define the expected outcome and the evidence required for acceptance. Run the tasks against the repository's current conventions and tooling when making important changes to the harness.
Track outcomes such as successful verification, architectural violations, human interventions, regressions, and execution cost.
This creates an agent-harness regression suite.
It answers a question ordinary product tests cannot answer:
Did our latest engineering change make the repository easier or harder for an agent to modify correctly?
Initially, these evaluations can be manual and limited to a handful of tasks. Automate them when the repository's complexity, change volume, or number of agents justifies the investment. Do not build a separate benchmark platform before you have enough experience to know which tasks predict real engineering performance.
12. Build the system in maturity stages
Do not attempt full autonomy on day one. Increase autonomy as the evidence and enforcement improve.
01

Reliable foundation
The project boots from a clean environment. A golden path exists. One command verifies the implementation.



02

Legible system
The agent can find authoritative specifications, understand module boundaries, run the application, inspect logs, and reproduce failures.



03

Enforced architecture
Repeated mistakes become shared primitives, stronger types, boundary validation, tests, and structural checks.



04

Evidence-driven changes
Changes include reproducible acceptance evidence. Critical verification paths are protected. Independent review focuses on ambiguous and high-risk changes.



05

Self-maintaining repository
Recurring agents identify architectural drift, maintain documentation, remove obsolete patterns, and open small cleanup changes.




Self-improving harness
Representative engineering tasks evaluate the environment itself. Changes to tools, conventions, and constraints are checked for regressions in agent performance.



Progress through these stages in response to observed failures, not a calendar. A small project may need only the first few stages for a long time. A security-sensitive or fast-growing system may need stricter enforcement much earlier.
13. What to measure
Do not judge this system by how many instructions, agents, linters, or tests it contains. Those are inputs, not outcomes.
I would track:
Metric	What it reveals
Recurrence of known failure classes	Whether the repository actually learns from mistakes.
Successful changes without human repair	Whether agents can use the system effectively.
Regressions that escape verification	Whether the quality controls catch real defects.
Time from failure to diagnosis	Whether feedback and diagnostics are useful.
Number of unrelated modules changed per feature	Whether the architecture supports local changes.
Verification bypasses and suppressions	Whether constraints are losing effectiveness.
False-positive rate of checks	Whether enforcement creates unnecessary friction.
Effectiveness of tests against deliberate mutations	Whether tests detect incorrect behavior, rather than merely execute code.
Use these metrics to decide where to invest next.
For example, if agents successfully complete most tasks but repeatedly introduce cross-domain coupling, invest in architecture boundaries. If the architecture is clean but agents spend multiple iterations reproducing bugs, invest in fixtures and operational tooling. If a large test suite repeatedly misses incorrect behavior, improve its oracles before adding more tests.
The objective is not to eliminate all errors. That is unrealistic. The objective is to make errors cheaper to discover, cheaper to correct, and less likely to recur.
14. The principles I would put on the wall
I would distill the entire doctrine into these rules.
1. The repository remembers what the team cannot afford to forget. Important knowledge must survive the chat session, the agent, and the original author.
2. The system must enforce what prose cannot reliably guarantee. Instructions explain; architecture and verification constrain.
3. Every recurring mistake is evidence of a missing capability. Do not respond to the same failure with increasingly elaborate prompts.
4. Prefer one strong primitive over many local rules. Reduce the number of independently invented solutions.
5. Every important change carries evidence. A completion message is not proof that the software works.
6. Verification must be independent enough to catch shared misunderstandings. Passing tests are only as valuable as the requirements they encode.
7. Diagnostics must explain the route to repair. A failure should direct the agent toward the correct next action.
8. Protect the system that judges correctness. Agents must not silently weaken their own tests, policies, or acceptance criteria.
9. Locality is a measure of architectural health. A small change should not require the agent to understand or modify the entire codebase.
10. Constraints must earn their complexity. Measure false positives, exceptions, and unintended consequences. Remove rules that make the system worse.
11. The repository must clean up its own entropy. Drift is continuous, so maintenance cannot depend on occasional bursts of human effort.
12. Test the engineering environment itself. A change that makes agents less reliable is an engineering regression, even if the product still passes its tests.
15. What I would actually do on the first day
I would not begin with a long AGENTS.md, an elaborate rule catalog, a fleet of specialist agents, or a custom framework. Those are easy ways to create the appearance of rigor without establishing a reliable path to working software.
I would establish the product contract, create one complete vertical slice, and make it possible to verify that slice from a clean environment. I would add a short repository map, one canonical implementation pattern, strict validation at untrusted boundaries, and the smallest test suite that meaningfully protects the feature.
Then I would use the agent to extend the system.
When it makes a mistake, I would fix the code. I would also ask why that mistake was possible, whether the failure is likely to recur, and what inexpensive structural improvement would prevent or detect it.
That improvement might be a type, a shared primitive, a regression test, an architecture check, better diagnostics, an operational fixture, or a more precise specification. It would be documentation only when the missing ingredient is genuinely knowledge that cannot be expressed more effectively elsewhere.
Over time, the repository should need fewer corrective instructions for the same class of work. The agent should spend less effort guessing how the project works and more effort solving the actual problem.
That is the real objective: not an agent that follows an increasingly long list of rules, but a software system whose design makes correct changes natural, incorrect changes detectable, and engineering knowledge cumulative.
