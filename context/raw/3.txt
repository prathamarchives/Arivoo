## 2. The most important mismatch: the execution plan still delays the product

The updated specification has ten foundation slices:

`F-00` repository and walls → `F-01` memory seed → `F-02` constraint toolchain → `F-03` harness → `F-04` database → `F-05` kernel → `F-06` schema → `F-07` command framework → `F-08` highlight capture → `F-09` scaffold.

The first real behavior appears at `F-08`, and it is a CLI capture path. The foundation then proves that fresh agents can add a note and bookmark. The reader and full journal workflow are not yet part of that path.

That conflicts with your locked choice: the first usable path is the reader, capture and journal experience, not a CLI-only backend milestone.

It also conflicts with a principle in the upstream engineering notes: establish a product contract, get one complete vertical slice working, and then improve the repository based on real engineering failures. The current plan builds a fairly extensive kernel and verification framework before it tests a real user workflow.

The answer is not to abandon the harness. It is to make the initial harness smaller and bring a real vertical slice forward.

### What I would change

Keep the high-risk guardrails from the start: isolated credentials, protected gates, a real database test, idempotent writes, immutable evidence, owner scoping, and an independent state read.

Do not require the complete constraint system, all custom architecture checks, every kernel primitive and every planned known-bad build to exist before product code is allowed.

Add each mechanism when it protects a concrete contract. Keep the harness capable of verifying the system from the beginning, and let the system and its constraints grow together.

The first usable workflow should be a milestone made from several small slices, not one enormous slice—and not something deferred until an arbitrary future version.

## 3. The first usable workflow needs a complete data path

The current specification says the owner will import books and articles, write in a journal, connect an agent, and reason while reading. But the initial `F-06` schema names `node`, `fragment`, `revision`, `behavior_event`, `tag_event`, `outbox` and `event_log`. The schema and slices do not yet define the complete source, import and journal path needed to deliver that promise.

Before the schema locks, the minimum durable model must account for:

- A work and its source version, separately from the imported file.
- A stable identity for a highlight, its committed text and its source anchor.
- A bookmark with a durable location.
- Notes and journal blocks with committed revisions.
- Stable `@` references to other objects, not just text that happens to look like a reference.
- Reading-session events and coarse location/dwell information.
- Local capture durability and cloud synchronization.
- Source provenance that survives re-parsing, renaming and re-indexing.

A highlight cannot be truly durable if it retains only its selected text but loses which book, edition, page or passage it came from. A journal reference cannot survive a rename if it stores only the visible title.

### The key durability distinction

Your existing architecture needs two separate outboxes:

1. Client outbox: preserves new work on the device and sends it when the cloud becomes available.
2. Server outbox: schedules enrichment jobs after the database transaction commits.

They solve different problems.

The UI should not claim that a capture is safe when it exists only in memory. I recommend preserving the durability ladder:

`local-durable → server-durable → keyword-searchable → semantically indexed → linked`

That provides honest recovery behavior and makes the "nothing is lost" promise testable across crashes and network outages.

## 4. Semantic enrichment is still written as a future layer

The specification currently says:

> "Meaning-based search comes later."

It also says the belief aggregation, concept induction and Kev classifier are archived layers that should not be built in the foundation.

Those instructions are incompatible with the architecture you have repeatedly locked. The revised document cannot tell agents that semantic memory is a fundamental capability and simultaneously classify the complete enrichment pipeline as out of scope without a precise implementation sequence.

There is a sensible distinction to make:

- The first capture slices do not need a fully calibrated autonomous belief system.
- The foundational architecture must provide for semantic indexing, vector retrieval, relationship processing and concept formation.
- The implementation sequence must reach these capabilities through small, tested slices instead of leaving them for an undefined later release.

I recommend making the first working capture path the immediate foundation, then adding semantic indexing and candidate retrieval as the next tightly scoped increments. Wire the real retrieval pipeline through the established contracts. Kev's automated decisions and belief promotion then receive their own policy and evaluation gates.

That is incremental implementation, not deferral.

The compounding probe must evolve accordingly. An early deterministic probe can prove that a known alias or explicit relationship makes an old highlight retrievable. A later semantic probe must prove that a new related work causes previously saved material to resurface through semantic retrieval. A subsequent graph probe must prove that automatic relationship creation adds useful connections without violating the evidence rules.

Those are progressively stronger claims, and they should be tested separately.

## 5. The purge decision needs an implementation contract

You have now selected purge as a requirement. The execution specification permits an owner-run purge as an exception to immutable evidence, but also says that no update/delete function exists and that database triggers reject both operations.

That is contradictory unless the purge path is explicitly designed.

I recommend the following behavior:

- Ordinary delete adds a tombstone. The object stops appearing in normal retrieval but remains recoverable.
- An authenticated account owner can request a deliberate purge of their own content.
- Runtime agents cannot invoke the purge capability.
- A protected purge operation removes the target content and its derived material, including embeddings, decisions, edge evidence, candidate records and unreferenced blobs.
- The operation leaves a minimal audit record consistent with the retention policy.
- Restores must apply the purge ledger before the restored database becomes available.

One policy decision still needs your judgment: what does purge mean for existing backups?

My recommendation is immediate removal from the live system and its active derived stores, with older backup copies expiring under a documented retention period. Restoring a backup must never silently reintroduce purged content. If you require immediate physical erasure from every backup, the backup design needs stronger mechanisms, such as per-owner encryption and key destruction.

This decision must be settled before the storage and purge schema is locked.

## 6. Behavior history and privacy need one canonical definition

You selected explicit actions plus reading sessions and coarse reading-position/dwell data.

The build playbook adds search history and agent-query history to its proposed event list. Those were not part of the selection you made.

The canonical scope should therefore be the narrower, explicit choice: user actions, source/session activity, and coarse reading-position/dwell checkpoints. Do not store raw keystrokes or mouse traces. Do not silently expand the policy to store complete search queries or agent prompts.

The specification should define the actual event vocabulary, recording cadence, retention policy and export behavior. It should also distinguish the text of a journal entry from behavior inferred about that entry. The event log should be enough to recover useful reading context without becoming an unrestricted activity-surveillance system.

There is also a security problem in the owner playbook. It instructs the setup process to inspect `env` as part of checking that the agent environment contains no secrets. Dumping the environment can itself expose tokens or sensitive variable values in logs. Replace that with a redacted isolation check that verifies required conditions without printing secrets.

## 7. Agent-written material needs a separate, attributed layer

Your goal includes connecting multiple agents, using them while reading, and eventually allowing them to work against Arivo through API or MCP.

The latest execution specification correctly says that agents never connect directly to the database and that writes carry an actor. But the canonical product contract should explicitly include durable agent-authored annotations, links and concept proposals.

These should be stored as attributed information about what the agent said or proposed. They remain retrievable, but carry zero weight in the belief calculation simply because an agent asserted them. A grounded text-pair decision or structural fact must still provide the evidence for an inferred relationship.

That distinction lets your agents contribute from day one without allowing their outputs to manufacture truth.

The API/MCP surface should enforce scoped reads, attributed writes, idempotency, bounded responses and stable error codes. It should expose the same application operations to the reader, CLI and agent adapters rather than allowing each client to invent a separate way to mutate the data.

## 8. Intent and terminology need one source of truth

Two more conflicts need to be resolved.

Archive authority. The current specification says the archive is the source of truth, while also instructing agents not to load it except during an Understanding Session or Scribe task. Historical documents contain superseded designs. The active Intent Ledger and explicit Decision Records should govern implementation; the archive should preserve provenance and history. Old decisions should be explicitly marked superseded rather than remain competing instructions.

The meaning of "fact." The stored owner wording defines facts as objective statements that can be verified and are known to be true. The revised architecture also says that a `fact` tag classifies a statement but does not certify its truth. These are not the same rule. The design needs a clear boundary between a factual claim and a verified statement. Do not let the Scribe or Planner decide this silently.

There is a related execution-rule issue: `understanding.yaml` requires zero unknowns, but the system has defaultable and non-blocking question classes. That requirement should become zero unclassified or unresolved blocking unknowns. Documented defaults and non-blocking questions can remain open without stopping unrelated work.

## 9. The harness and language standards

The local-plus-remote trust model you selected is right. Local `make verify` helps the builder. The owner-controlled CI gate is authoritative. The agent must not control the signing key or weaken the checks.

Host compatibility must be tested rather than assumed. Current Codex CLI documentation says it loads applicable `AGENTS.md` files automatically. Claude Code documents `CLAUDE.md` memory files and their ability to import other files using `@path` syntax. A small host-specific bridge to the canonical instructions is therefore reasonable, as long as the actual loading behavior is verified on the installed versions. 

There is a subtle trust issue in CI too: a required status check named `verify` is not enough if untrusted integrations can supply that status. GitHub documents the ability to restrict a required status check to an expected source application. Use that capability where available so the trusted gate is not merely a string with the right name. 

The STE-style language experiment is appropriately treated as an experiment. Issue 9 of ASD-STE100 is the current official issue, dated January 2025. It is a controlled language standard for technical documentation, not proof that every one of its sentence rules improves agent code. Keep the A/B test and let the measured result decide how strictly the profile is enforced. 

## 10. What the next execution pass should do

I would not write all the slice cards now. First, reconcile the canonical specification with the decisions above.

Then use the first few slices to establish one verified line from user intent to actual behavior:

1. Execution environment and trust: name the initial supported hosts, verify Windows/WSL execution, protect the repository, establish the trusted local/remote gate, and prove the sandbox cannot expose secrets.
2. Minimum trustworthy harness: run one real-stack test, generate a Proof Sheet from run records, enforce scope, and prove that representative deliberately broken builds fail. Do not require every future product-specific failure case before product behavior exists.
3. Durable capture: create the minimum schema and API contract for a source-linked highlight, with stable identity, anchor, immutable revision, owner scope, actor attribution, idempotency and recovery.
4. Reader and journal path: incrementally add opening a PDF/EPUB, highlighting, bookmarking, margin notes, durable journal blocks and `@` references. Each behavior gets its own small card and verified result. The complete reader-capture-journal path is the first usable milestone.
5. Retrieval and compounding: bring keyword lookup, agent reads and semantic indexing into the working system, then validate the relationship and concept-enrichment pipeline through the actual capture-to-retrieval path.

That is not a replacement roadmap with distant versions. It is the first sequence of small slices. We only plan beyond the next active phase when evidence from the current phase tells us what is needed.

## 11. The remaining owner decisions

Only three questions need an owner answer before the corresponding design locks.

1. Which exact host does "Other" mean, and which host will be the primary builder for the first slices? I recommend one primary builder for predictable execution, with a verifier from a different model family where possible. The other named hosts can pass the same host contract before they are considered supported.

2. What does purge mean for backups? I recommend immediate removal from live data and active indexes, with a defined backup-expiry period and a purge ledger that prevents restored data from resurfacing. Confirm that boundary before storage and purge design is locked.

3. What does the `fact` tag mean? Does it mean "a statement intended to be factual, with its evidence and verification status recorded separately," or "a statement the system treats as verified true"? I recommend the first interpretation because it supports disagreement and uncertainty without losing the source claim. But the original owner wording points to the second, so this needs an explicit decision.

The calculation-engine question can remain open and non-blocking for the initial capture path. It should be revisited when the math workflow is designed, distinguishing equation display and extraction from numerical calculation, symbolic algebra and arbitrary code execution.

Bottom line: the new context strengthens the execution system, but I would revise its phase order and canonical product contract before freezing it. The biggest priority is to stop the verification framework from delaying the very workflow it exists to protect. Build the first reader-capture-journal path through small slices, prove every slice against the intent, and keep semantic enrichment in the active implementation sequence rather than an archived future layer.
