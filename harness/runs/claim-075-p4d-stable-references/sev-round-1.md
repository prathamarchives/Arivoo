## §4 Findings

- **F-075-1 — P2 — open.** An all-digits pin of ≥4301 characters crashes the parser with an untyped traceback instead of the promised ARV-REF-002. Live evidence: `resolve-reference --ref note:<live-uuid>@` + `'1'*5000` (and `'1'*4301`) → exit 1, stdout EMPTY, stderr carries `Traceback … ValueError: Exceeds the limit (4300 digits) for integer string conversion`; the same at exactly 4300 digits refuses cleanly (`FAIL ARV-REF-001`). Root cause: `_ref_parse` calls `int(rev)` after only `rev.isdigit()` — CPython 3.11+ raises above the 4300-digit int-str limit. Fail-closed (no answer, no write, no leak), but the hostile-string law's "never clamped, never a guess, the named refusal" is violated on this input class, and the internal traceback leaks to stderr. Disposition/repair routing: a pin-length bound before `int()` (e.g. `len(rev) > 9` → ARV-REF-002 "the pinned revision is not a plausible revision") in query.py `_ref_parse` — a one-line strengther for the slice's follow-up commit or P4-E; the suite's hostile battery should add the all-digits oversize form (the landed battery's 10k form is non-digit and passes).
- **F-075-2 — P3 — open.** A trailing-newline id passes the uuid grammar and produces an untyped read failure. Live evidence: `--ref "work:<work-uuid>\n"` → `FAIL ARV-QRY-002: the read failed — ERROR: invalid input syntax for type uuid: "01a1ca0…"` at exit 1 — not ARV-REF-002. Root cause: `_REF_UUID_RE` ends in `$`, and Python's `$` also matches just before a trailing `\n`, so `"<uuid>\n"` passes; the SQL cast then fails. Fail-closed. Repair: `\Z` instead of `$` (or a literal `\n` rejection) — note the substrate's `_UUID_RE` (commands.py:1191) shares the same `$`, so the repair belongs to both boundaries at once.
- **F-075-3 — P3 — routed.** Unicode-digit pins (`@١`) and leading-zero pins (`@0001`) are accepted and normalized to pin 1. Live evidence: `note:<id>@١` → `{"pinned_revision": 1, … "state": "historical"}`; `@0001` likewise. This is the CLAIM-057 substrate's own `isdigit()` law (commands.py:1219) composed verbatim — narrowing it here would be a second implementation. Routed to the substrate's grammar owner (tighten both boundaries together if ASCII-only pins are wanted).
- **F-075-4 — P3 — owner-accepted-debt.** An uppercase-hex uuid resolves and is echoed case-preserved. Live evidence: `highlight:<UUID-UPPER>` → current, `"id": "01A1CA08-…", "resolved_ref": "highlight:01A1CA08-…@3"`. The regex allows A-F (same as the substrate) and Postgres uuid comparison is case-insensitive, so the identity resolves; the echo is not canonicalized to the stored lowercase form. Consistent with the substrate and RFC 4122 case-insensitivity; cosmetic identity-echo debt only.
- **F-075-5 — P3 — routed.** The landed resolve-anchor arm does not consult the purge ledger. Live evidence: after `INSERT INTO arv.purge_ledger (… 'anchor', <anchor-id> …)`, `resolve-reference anchor:<id>` answers `purged` (correct — the precedence) while `resolve-anchor --id <id>` still answers its P3-03b verdict (`resolved`). This is pre-existing landed behavior outside this slice's diff (the slice was forbidden from modifying landed arms); the purge-awareness of the other read arms belongs to D-011's governed-purge command slice. Routed there.
