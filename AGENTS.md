## What this is
- **Objective (INT-093):** any capable agent can enter this repository, understand the project, identify the next correct action, work within its authority, verify its work, and leave the repository easier to continue from. Every structure below exists to make that true without the agent supplying its own assumptions.
- **Arivo**: the owner's reading/study/reflection environment — backend only (base, foundation, mechanism; no UI/UX). Repo: **Arivoo**. Owner: prathamarchives.
- Phase: **PHASE 3 ENTRY DIRECTED (2026-10-19, session 19, owner turns 17–19, INT-122..INT-124/D-037/D-038 — the NG-04 gate opened by the owner's own turn: the execution contract lands first (the systems design before code; a systems-engineering verification required after every implementation slice), then the bounded H-01/H-02 gates (the base-anchored harness floor; the SEV report/gate), then the Phase-3 product slices. The repo is a MULTI-AGENT workspace by directive (D-038, turn 19): coordination through `CLAIMS.md` — claim-before-work, scope exclusivity, intent-ID reservation; any capable agent may hold a claim; the walls remain the single merge serializer. Do not claim a guard is enforced until its known-bad proves it.** 106 statused intents; open register: D-014 + Q6–Q12 (each blocking only its named dependents); remote CI (`verify` workflow, D-009/D-025) runs the verifier, the base-anchored isolation checker, AND the harness gate on every PR with ALL THREE required checks (`canonical-layer`, `head-tools`, `harness`) bound to `main`; all four walls live.
- Operating mode: the orchestrator runs, the owner reviews (P-13). Commit protocol: memory deltas land as a commit and a push (P-15); analysis/review/proposal artifacts land by PR, merged only with the owner's explicit authorization (D-024).

## Binding rules
- The repo is the memory. Chat history is not (P-02). Every reasoning delta → file → commit → push (P-15).
- **Change channel (D-024): findings are recorded; changes are applied only through reviewed branches.** Analysis, review, and proposal artifacts NEVER land on `main` directly — they arrive on a branch, through a pull request, and merge only with the owner's explicit authorization. Memory deltas (owner words, decisions, ledgers, worklog, plan, session records) land per P-15: branch + PR + merge under the standing authorization of P-13/P-15 (the owner reviews at gates, not per-merge). With walls stage-1 live, direct pushes to `main` are rejected by the host.
- **Multi-agent coordination (D-038/INT-124; LAW-31):** the repo is a multi-agent workspace — never assume you are the only agent. No consequential change without an OPEN claim in `/CLAIMS.md` whose declared scope covers its diff; two OPEN claims never overlap on a non-shared file; ledger IDs are reserved one-at-a-time through the registry (each exactly previous-max+1); the shared-append class (INTENT-LEDGER, DECISIONS, context/WORKLOG, CLAIMS, STATE, the manifest, session records under their own IDs) is overlap-legal but append-shaped only; STATE conflicts resolve by re-derivation (a snapshot, never authority); the walls remain the single merge serializer. A PR whose branch carries no OPEN claim is refused by the gate once the machinery is live (ARV-CLM-001..004).
- Owner intent enters ONLY through INTENT-LEDGER entries (verbatim, statused). `context/raw/` is the verbatim corpus as received from the owner — mixed owner statements, AI analysis, and pasted documents. Never edit it; never treat a raw sentence as owner intent by itself (source tiers: `/EXECUTION.md` §2).
- Ledgers and logs are append-only: supersede by referencing; never rewrite history. One fact, one home; every duplicated fact creates a synchronization obligation.
- A law is a constraint WITH a check (LAWS.md). No product code, dependencies, or CI until the owner approves the execution plan. Documents (memory, laws, plan) are the authorized first layer.
- Do not weaken constraints, thresholds, or checks. The verifier is protected. Do not touch gates/workflows once walls are live — wall CONSTRUCTION per an owner directive is the only exception, and it lands with evidence (D-025's CI + required-check binding is the example). A separate systems-engineering verification is required after every implementation slice (INT-122/D-037/LAW-30). An agent may not close owner decisions, promote an unadopted proposal, or merge its own analysis/review proposal.
- **Credentials hygiene (D-025):** access credentials (PATs, tokens, keys) NEVER enter repo files, worklogs, session records, ledgers, or logs — an owner-supplied credential is used for the session and redacted at ingestion (INT-092). `tools/isolation_check.py` scans tracked files for secret value patterns; a hit is a P0 repair (rotate the credential, scrub history) before any other work.
- Evolving truth (P-18): documentation updates repair what the CURRENT task needs — fix contradictions that could mislead current work; leave unrelated editorial debt for the post-product comprehensive refinement pass; supersede properly, never rewrite. Most importantly, never let stale documentation cause a real implementation mistake.
- Owner words verbatim, typos preserved; interpretations always labeled. Contradictions: name both, Question Record, authority order (`/EXECUTION.md` §3) — never average, never silently choose.
- Slice cards and context packs carry their INT- IDs and the owner quotes (LOOP-05: a requirement with no intent behind it fails the audit).
- The owner-facing build playbook is intentionally NOT in this repo (INT-034). Do not add it.
- Isolation/secrets checks print conditions, never values. No `env` dumps.
- Language: English. Tailored, technical, machine-readable, clean. Stable IDs; reason codes on failures; one fact, one home.
- Test and verification loops run on fresh-context subagents; the protocol is host-agnostic by design (D-028) — any capable model family may run it, GLM being the current default (INT-070), never a requirement; independence comes from the verification design, not the model brand (INT-117/OPERATING-MODEL §9).
- Bounded diffs (D-026/INT-099): every PR carries one coherent purpose and a bounded diff; implementation and revert changes are proposed separately when appropriate; every PR follows the PR contract (`.github/PULL_REQUEST_TEMPLATE.md`, the form of the review protocol §8).
- Session exit (every agent, every session): append your WORKLOG entry, update `/STATE.md` (its five-area contract, GLOSSARY: position, work — active task vs exact next action, dependencies — every unresolved owner question, evidence — labels with one direct pointer per claim, coordination snapshot), commit every reasoning delta, push, and — if any root document changed — run `python3 tools/verify_canonical_layer.py` and land it green (P-15, INT-072, INT-074). EVERY meaningful session (GLOSSARY, event-typed) appends a compact WORKLOG entry (100–250 words: task, outcome, evidence, pointer, unresolved, next action — form: `context/TEMPLATES.md`); SUBSTANTIAL work (GLOSSARY, event-typed — implementation slice, multi-step investigation, review with findings, verification campaign, architecture decision, failure investigation, coordinated multi-agent work) also leaves a numbered session engineering record in `context/extracted/` with the mandatory standardized fields (form: `context/TEMPLATES.md`; actual commands with exit codes, never reconstructed; results and conclusions, never private reasoning; the record's §1 preserves the owner's turn verbatim BEFORE the ledger entry is written — the INT-046/068 class, closed 2026-10-14; two-tier policy D-027/INT-106 supersedes the single-tier INT-072/F-04 rule by reference).
- Layer check: `python3 tools/verify_canonical_layer.py` — the canonicalization conditions on the real files; green means the layer is coherent. Remote CI runs the same check authoritatively on every PR (D-009/D-025): local green is preflight, the remote run is the proof. The verifier never implements what it evaluates — testing/falsification runs on fresh-context subagents; a second model family is optional adversarial coverage, never an unexplained prerequisite (INT-117/OPERATING-MODEL §9).
